# hybrid/ - running the open code inside the real driver

`open/` reimplements parts of Broadcom's object from specifications, and the
A/B tests show that each part does what the object does. But the module that
actually runs, `bcm4360.ko`, still links the whole object, so until now none
of that open code ran on a real card and the driver relied on closed code as
much as ever.

The **HYBRID build** changes that. It replaces whole layers of the object,
inside the existing driver, with the open code:

```
make HYBRID="access pmu mac"          # or: scripts/hybrid-build.sh
```

The default build (`make`, DKMS) is unchanged. HYBRID is experimental and
opt-in: it has passed every test the emulator can run and builds against the
target kernel, but it has not run on a card yet (see "State").

## How it works

Broadcom's object is one relocatable ELF file. Every call from one of its
functions to another named function is a relocation against the callee's
symbol: `tools/re/hybrid.py redirect` checks this for every replaced function
and finds no call that bypasses it. So the linker can send those calls
elsewhere:

1. A copy of the object is made (`objcopy`, rule in `hybrid.mk`) in which the
   replaced functions are global and weak. They are local in Broadcom's
   object; the functions the bridges call are made global too.
2. A **bridge** (`hybrid/<layer>.c`) defines the same names with the object's
   arguments. The linker resolves every call of the object to the bridge's
   strong definition. The object's own copy stays in the module but is never
   called.
3. The bridge copies the state the open function needs out of the object's
   structures (`blob_abi.h`: field offsets, as the specifications give them),
   calls the open code, and writes the state back. It contains no behaviour
   of the object, only this marshalling. It lives here and not in `open/`,
   because it exists only as long as the object does.

The open code reaches the hardware through `open/include/bcm4360/hw.h`.
With `BCM4360_OSL` (set by the HYBRID build) that header uses the driver's OS
layer, `src/shared/linux_osl.c`: the same `osl_readl()`, `osl_delay()`, ...
that the object itself calls.

## Layers

| Layer | Replaces (functions of the object) | Open code |
|---|---|---|
| `access` | `phy_reg_read/write/mod/and/or`, `read/write/mod/and/or/xor_radio_reg`, `wlc_phy_table_write/read_acphy`, `wlc_bmac_read/write_shm` (15) | `open/hw/access.c` |
| `pmu` | `si_pmu_init`, `_pll_init`, `_res_init`, `_measure_alpclk`, `_chipcontrol`, `_regcontrol`, `_pllcontrol`, `_pllupd`, `_alp_clock`, `_ilp_clock`, `_si_clock`, `_get_bb_vcofreq`, `_fast_pwrup_delay`, `_otp_power`, `_is_otp_powered`, `_rfldo` (16) | `open/chip/pmu.c` |
| `mac` | `wlc_bmac_mctrl`, `wlc_ucode_wake_override_set/clear`, `wlc_bmac_suspend_mac_and_wait`, `wlc_bmac_enable_mac`, `wlc_bmac_mhf` (6) | `open/mac/bmac_ctrl.c`, `open/mac/bmac_mhf.c` |

`<layer>.weaken` and `<layer>.globalize` are generated by
`python tools/re/hybrid.py symbols LAYER --write` from the compiled bridge;
do not edit them by hand.

## State

**Emulator** (`tools/re/hybrid.py`). The object, with the layers' calls
pointed at the bridges, runs the session of the PHY scenarios (attach, up,
nine channel changes in both bands and all bandwidths, watchdog, down).
Every bus access is compared with the same session of the object alone:

| Layers | Functions redirected | Calls (relocations) | Bus accesses | Differences |
|---|---|---|---|---|
| `access` | 15 | 11,624 | 76,781 | 0 |
| `pmu` | 16 | 118 | 76,781 | 0 (*) |
| `mac` | 6 | 106 | 76,781 | 0, even counting the window moves |
| `access pmu mac` | 37 | 11,848 | 76,781 | 0 (*) |

(*) The object moves the BAR0 window to ChipCommon and back around each PMU
access; the open code uses ChipCommon's fixed window instead, so 42 window
writes (13 places) are absent. The card model names every access by the core
it actually reaches, so the comparison still catches any access that lands
on the wrong core. `hybrid.py run` prints both counts.

With all three layers, 36 functions of the object no longer run in that
session; **8.9% of everything the driver executes is open code** (every PHY
and radio register access, the PMU, the MAC control path); 5,062 bytes of
the 189,946 bytes of object code the session runs are no longer used
(`hybrid.py metric access pmu mac`).

**Kernel build.** Built in an Arch Linux container against
`linux-headers 7.2.11-arch1-1` with GCC 16.2.1 (the target system runs
7.2.7-arch1-1 with the same compiler): no warnings from `open/` or `hybrid/`.
In the linked module each of the 37 names has exactly one strong
definition, the bridge's, and the module's relocations against them match
the emulator's counts one for one.

**Not yet verified: a real card.** The emulator models the card with assumed
identity values (`docs/re/05-status.md`), and its session does not cover
scanning, association, data traffic, roaming, suspend/resume or the card
being removed. The replaced functions are used on those paths too.
Known difference: the open suspend (`mac` layer) leaves out the object's
handling of a removed card (all registers reading 0xffffffff); it waits for
its normal time-out instead.

## Trying it on the card

```
scripts/hybrid-build.sh                    # builds into /tmp/bcm4360-hybrid, checks the symbols
```

It prints a `swap-test.sh` command that loads the hybrid module in place of
the running one, checks association, address, gateway, internet and DNS,
reconnects three times, checks the kernel log, and goes back to the
installed `bcm4360` by itself if anything fails. Start with `access` alone
if you want the smallest step: `scripts/hybrid-build.sh access`.

## Found on the way

The whole-session comparison caught one place where the object itself is
not deterministic: `sub_09eaf9` (the AC-PHY's update of register tables on a
bandwidth change) passes the address of a 32-bit variable on its stack to a
transfer of one 48-bit entry of PHY table 0x14 (offset 0x33). The third
16-bit word of that entry is whatever lies on the stack next to the variable
(0x8080 in some calls of the emulated session, 0 in others). The open PHY
reproduces 0x8080 (`docs/re/questions/phy-rxgain.md`), but that is an
emulator artifact, not a value the object defines. `hybrid.py` compares that
word as undefined.

## Next layers

The PHY as a whole: it is fully encapsulated at runtime (in a whole session
no code outside the PHY files touches its memory, and the PHY touches no
memory of the MAC), so all of `wlc_phy_ac.c` and `wlc_phy_cmn.c` (38% of the
object code a session runs) can be replaced at its 83 entry points once the
PHY API layer is specified (`docs/re/spec/phy-cmn.md`, in progress). Then the
rest of `wlc_bmac.c`, the backplane (`siutils.c`, `aiutils.c`, `nicpci.c`),
SROM/OTP and DMA.
